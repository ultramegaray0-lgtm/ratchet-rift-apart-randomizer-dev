# Rift Apart Enemy Randomizer V3.0 — Alpha

Status: **V3.0 engineering alpha; offline build and in-game acceptance are separate gates.**

## Objective

Attempt replacement at every structurally eligible, reachable enemy-owned spawn point across the game's planets while leaving the original encounter system in charge of actor creation, death events, wave counts, doors, and progression.

V3.0 does not claim that every actor or every archived zone is an enemy spawn point. Civilians, vehicles, pickups, props, bosses, scripted allies, hazards, malformed references, and unreachable archive assets are not ordinary enemy candidates.

## What V3 adds

### 1. Hybrid factory + node-adapter stage path

- Native `SunsetSpawnerFactory` `Templates` variables continue through the validated local-zone `.stage` writer.
- A new experimental offline planner handles only exact `SpawnerScriptAction` nodes with one `Template` plug, a consistent local actor reference, a regular enemy original, and a single-owner variable.
- Node replacements are selected from local enemy templates already referenced by native factory or exact spawner nodes in the same zone.
- The node planner requires a same-faction / same-movement pair or known positive pair evidence, and retains an unchanged anchor user for every selected replacement.
- Shared, malformed, multi-plug, external, non-local, unknown, and generic Template nodes remain native and receive an explicit inventory reason.
- V3 factory changes are single-owner only; shared factory variables are left for the runtime planner, which applies its own shared-variable freshness rules.
- The manifest records each change's adapter type. The stage monitor checks both factory and node Template spawns.
- Runtime writes are blocked only for factory and node Template keys explicitly listed in the V3 manifest. Unchanged factory, node, and group adapters remain eligible for the runtime route, including its resident global-template pool.

### 2. Native global-template diagnostics

The custom Rivet Hook patch now distinguishes a native spawn exception, a null actor return, and an unreadable actor pointer. Null-return failures include the loaded asset ID, native asset status, and actor path in the returned diagnostic. This does not magically make the 11 previously failing assets spawnable; it gives the next run enough evidence to investigate those failures precisely.

The native hook is rebuilt by the `Build Global Enemy Registry Hook` workflow when its patch changes. The V3 diagnostic build passed all native compile and artifact-upload steps: [run 45737538654](https://github.com/ultramegaray0-lgtm/ratchet-rift-apart-randomizer-dev/actions/runs/45737538654). Download [the V3 Rivet Hook artifact](https://api.github.com/repos/ultramegaray0-lgtm/ratchet-rift-apart-randomizer-dev/actions/artifacts/15080161752/zip) (7.37 MB) and replace the existing `rivet_hook.dll`, `hid.dll`, and `hid_win10.dll` after backing them up.

### 3. Full synchronized runtime bundle

The installer now packages and backs up the complete runtime script set as one kit, rather than replacing only the enemy scripts. All scripts use kit stamp `10.0.50`; the stage Lua handshake remains `1.1.0`.

This prevents the mixed-script condition seen in the previous log (the main kit reported 10.0.43 while the installed spawner script reported 10.0.39).
- The independent build checker now validates all 18 runtime script stamps against `R.KIT_VERSION`, the `04_rando_settings.lua` maximum-coverage defaults, the stage monitor handshake, and the presence/content of both generated manifests. The installer refuses incomplete or mixed V3 bundles before writing to the game folder.
- The expanded offline validation, including the mixed/missing-bundle rejection tests, passed in [workflow run 45741846348](https://github.com/ultramegaray0-lgtm/ratchet-rift-apart-randomizer-dev/actions/runs/45741846348).

### Runtime fallback policy

The synchronized V3 settings explicitly set `enemy_compat = "max"` and `enemy_mix_movement = true`. This is intentional maximum coverage: the runtime route can mix walker, flyer, and turret templates, while the stage planner remains same-faction / same-movement constrained. The existing combat watch and five-retry safety net remain active, but they do not prove every replacement is reachable or progression-safe. Watch encounters carefully during acceptance testing.

### 4. Separate coverage accounting

The generated report now distinguishes:
- factory spawners discovered / changed;
- exact `SpawnerScriptAction` node candidates;
- structurally eligible single-owner local node adapters;
- node adapters changed;
- total stage changes.

A written `.stage` change is not counted as an in-game successful replacement. Runtime verdicts remain separate.

### 5. New build entry point

Run `BUILD_V3_0_MAX_COVERAGE.bat` from this folder. It:
1. scans the user's actual game archives;
2. builds the V3 hybrid profile and a factory-only safe fallback;
3. runs the independent byte-level `.stage` check;
4. offers installation only after the check passes;
5. backs up every runtime script and the stage files it replaces.

The V3 profile is local-zone only. It does not use foreign-zone actor UIDs or `--force-all-enemies`.

## Baseline and remaining gaps

The last supplied all-game scan (2026-11-25) reported:
- 32,300 zone assets in the DAG;
- 9,046 zones scanned, 8,599 decoded, 447 not decodable;
- 23,254 zone assets not in the TOC scan;
- 1,324 factory nodes, including 935 classified enemy factories;
- 638 other Template-adapter census entries;
- 170 factory changes (18%) in the conservative build.

These are baseline figures, not V3 results. The V3 builder must run against the current local game installation to produce actual V3 totals. The 638 Template census entries are not automatically 638 eligible enemies.

The global native asset catalog previously contained 25 actor assets: 14 resident template creations succeeded and 11 failed with `SpawnActorFromAsset failed to create the template actor`. This is still a runtime coverage limitation. V3 does not pretend those 11 are solved.

## Acceptance gates

### Offline gate
- Python compile and unit tests pass.
- Lua syntax and stage-monitor tests pass.
- The V3 build's independent `.stage` checker passes every changed zone.
- Every change has a local UID/index match, a valid adapter owner, and an unchanged replacement anchor.
- The inventory gives a reason for every skipped node.

### In-game gate
- Each patched factory and node adapter is observed using its replacement.
- Replaced enemies can be killed and disappear correctly.
- Encounter wave counts complete; doors and progression advance.
- No softlocks or progression blockers appear across the tested planets.
- Failed and untested pairs are fed back into the next verdict-guided build.

Until both gates are satisfied, V3.0 remains an experimental alpha. The target is 100% of eligible reachable enemy spawners attempted; the actual success rate must come from the runtime log, not the build report.
